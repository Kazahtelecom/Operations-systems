Блок 0. Разведка: ps, /proc, chrt
В ходе первичного осмотра системы
были изучены атрибуты планирования текущих процессов.

Команда ps -eo pid,ni,pri,cls,comm показала,
что большинство системных процессов имеют класс TS (SCHED_OTHER) и приоритет NI=0.

Проверка текущего шелла (PID 299) через /proc/$$/stat выдала: PRI=20, NI=0.

Команда chrt -p 299 подтвердила использование стандартной политики SCHED_OTHER с приоритетом 0.

Блок 1. nice — запуск с приоритетом
Был произведен одновременный
запуск двух процессов dd с разными значениями вежливости.

Процесс PID 540 запущен с nice -n 0 (PRI=20).

Процесс PID 541 запущен с nice -n 19 (PRI=39).

В выводе ps у низкоприоритетного процесса в
колонке STAT появился флаг N, что означает "low-priority nice". При нагрузке планировщик CFS выделял значительно больше ресурсов процессу с NI=0.

Блок 2. renice — изменение на лету
В этом блоке
была проверена возможность изменения приоритета уже запущенного процесса.

Процесс был запущен с дефолтным NI=0.

Команда renice -n 10 -p 547 успешно изменила значение nice на 10.

Попытка вернуть приоритет командой renice -n 0 -p 547 привела к ошибке Permission denied.
Вывод: Обычный пользователь в Linux
имеет право только увеличивать
значение nice (понижать приоритет). Повышение приоритета доступно только суперпользователю.

Блок 3. Эксперимент: nice и время выполнения
Для чистоты эксперимента была создана фоновая нагрузка на CPU
(4 процесса dd). После этого запущены два конкурирующих процесса через time.

Результаты: Процесс с nice 0 завершился
значительно быстрее (параметр real), чем процесс с nice 19.

Анализ: Планировщик CFS использует веса
для распределения квантов времени.
Разница в весах между nice
0 и 19 составляет примерно 68 раз, что напрямую 
отражается на времени выполнения
(параметры user и sys показывают затраченное 
процессорное время, но именно real время демонстрирует задержки из-за ожидания очереди).




При нагрузке планировщик выделяет процессу с nice 0 значительно больше ресурсов, тогда как процесс с nice 19 работает по остаточному принципу, что видно по низкому проценту %CPU в выводе ps
